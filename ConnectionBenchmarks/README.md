# Controlled browser-connection measurements

Run `Run-Comparison.ps1` on the same Windows x64 computer, after other builds and test browsers finish. The default run rotates direct, actual verified Tor, and Proton extension enabled in a fresh **signed-out, unconnected** profile across three trials. Each case has five identical local documents and five one-second samples for each Idle and Active phase: nine cases and ninety samples when all three modes complete. `-Latency` adds three HTTPS Example Domain navigations for direct and Tor, recorded separately; it deliberately does not present signed-out Proton as a connected proxy-speed test. `-SkipBuild` runs a previously coordinated build.

Every case requires a new empty output folder. The harness opens an offscreen standalone WPF host and raw WebView2 controllers, not the installed Harbor or its personal profile. It never signs in, requests credentials, edits provider files, or changes Windows networking. It removes only its own test extension registrations and stops its exact owned Tor helper. Profile/data folders stay under this harness's TestResults; exclude them from shared archives.

The resource sampler includes the harness host, **all process IDs reported by its WebView2 environment**, and the exact `tor.exe` PID owned by BrowserVpnService. Process start times guard CPU deltas against PID reuse. Missing or unverified Tor fails a case. JSON separates Host, WebView2 and Tor memory and records the total. Public IPs, provider state/credentials and Windows proxy values are not written to evidence; only the unchanged-proxy boolean is recorded.

Each fixture touches 8 MiB and creates 300 DOM rows. Idle runs no page timers. Active explicitly invokes approximately eight milliseconds of JavaScript work on each page about every 100 ms; all controllers use the same hidden/offscreen configuration in every mode. The provider popup is briefly initialized for startup/readiness observation, then closed before steady samples. A fresh signed-out profile has no provider login. Failure to render its sign-in UI is recorded as unconfirmed readiness, not repaired or called a successful connected session.

This compares **fixed connection/background overhead plus a local script workload**, excluding Harbor's full application UI. Local virtual-host pages do not traverse the Tor network, so samples do not measure sustained encryption/transfer cost. Cold environment/provider setup and optional external navigation timings are separate columns. Battery consumption, full application responsiveness, packet-level privacy and long-session performance are unmeasured. Working-set sums may double-count shared memory; private commit is not exclusive physical RAM. CPU is normalized by logical processor count. These short local trials do not establish a universal resource budget or that a connected Proton session is lighter than Tor.

A connected Proton comparison needs a separate user-driven sign-in in the isolated trial and an actual route proof. It must use a coordinated, closed test profile and the same workload. This harness intentionally does not accept arbitrary existing profile paths or copy saved account tokens, and must not be pointed at the installed browser's profile. Extend the live mode only after that handoff is explicitly arranged.
