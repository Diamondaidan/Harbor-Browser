# Updating Harbor

Open Help > Check for updates, or Tools > Updates and backup recovery. Checks happen only when requested. They contact the public GitHub release feed using the Windows connection, without browser cookies or account credentials. If Proton or Tor is enabled, checks and downloads pause; change that connection yourself when appropriate. A cached, already verified package can be prepared for setup without downloading it again.

Harbor displays the signed release notes and version, and labels an installed release candidate as RC1 (or its later RC number). A candidate may update to the full release of the same base version. A full release will not offer itself again, and neither channel offers older versions as ordinary updates. The helper reads the actual running browser's executable resource before accepting a same-version RC-to-full handoff; an editable plan flag is insufficient.

Download update retrieves the installer into a content-addressed Updates/Downloads cache inside the Harbor profile. Pause keeps a partial transfer. Another Download attempt resumes only when a strong ETag and the exact signed package identity match. HTTP 200 resets the partial file; invalid ranges and oversized/encoded responses are refused. A full size/SHA-256 check is always required before setup.

Choose Close Harbor and open setup explicitly. Save forms and finish downloads first. A copied helper, running outside the installation folder, verifies the release again and keeps a read lock on the exact installer through setup. It verifies the original process identity, waits for its exit, acquires the profile lock, makes a data snapshot, and opens interactive setup. Windows approval cannot be accepted by Harbor. Canceling or failing preparation does not trigger a silent install. Later update status reports the previous attempt's result.

Recovery offers only the previous version approved for the exact installed release and the same profile format. Version 0.6.0 and the prepared 0.5.7 target both use schema 9. Newer/incompatible profiles are refused. Snapshots contain Harbor JSON/state files and per-file hashes under UpgradeBackups/update-*. Account databases are neither copied nor removed. Open profile backups exposes the folder for manual recovery; incomplete folders without snapshot.json are not complete new-format snapshots. Older Inno snapshots are retained as historical backups. An app rollback retains the current compatible profile; it does not automatically restore historical browsing data or account state.

## Publisher preparation

Repository: https://github.com/Diamondaidan/Harbor-Browser . The client uses https://github.com/Diamondaidan/Harbor-Browser/releases/latest/download/harbor-update.json and exact versioned installer assets named HarborBrowserSetup-VERSION-release.exe under tag vVERSION. The latest published full release is 0.7.0 as verified November 25, 2026. A failed check reports unavailable; it must not be interpreted as an up-to-date result. Local 0.7.1 RC1 is ahead of that feed and is not offered by it.

VERSION.txt and RELEASE-CHANNEL.txt control source build identity. Full releases use plain ProductVersion metadata; candidates use VERSION-rc.N. App, helper, package manifest and installer must match. The stable signing tool rejects RC metadata, even if the candidate file is renamed to a release filename. Stable manifests retain their existing numeric version/schema format for compatibility with older clients. The installation marker HarborStable identifies the established app/profile family, not whether the compiled build is an RC.

The initial release public key is embedded in the app. Its separate private key was generated locally and encrypted to the current Windows account, outside this source folder in the sibling Harbor-Release-Signing/updates-v1.dpapi. No private key belongs in source, release assets or GitHub. The publisher needs this Windows account/profile to decrypt that file; copying the encrypted file alone to another Windows account is not a usable recovery method. Keep an appropriate owner-controlled backup of the account/key environment. Losing the key requires a separately installed release with a new trust root. This release does not implement automatic root-key rotation or the full TUF protocol.

ReleaseTools/New-Update-Record.ps1 creates the signed harbor-update.json after installers are finalized. Supply Installer, PrivateKeyPath, Sequence, OutputPath, optional PreviousInstaller and NotesPath. Use AllowUnsigned only for intentionally unsigned installers. Sequence must increase for every changed record. Records expire in 14 days by default (maximum 30); renew before expiry with a higher sequence even when the app version is unchanged. Never change a published package's bytes without creating a new release/record. Use a new output path; the tool refuses overwrite.

ReleaseTools/Sign-Release.ps1 prepares Windows signing using an existing code-signing certificate thumbprint and its provider's HTTPS timestamp URL. No certificate was purchased, created or trusted automatically. It signs with SHA-256 and verifies the result with SignTool. The installer builder optionally accepts SigningThumbprint and TimestampUrl. Sign app/helper before final testing; sign the final installer before making the update record. A signed installer's certificate hash is pinned by its release record, and the client also requires Windows trust verification. Windows trust checks use cached evidence, without background network retrieval; insufficient evidence fails closed. Without a Windows certificate, the separate Harbor release signature still authenticates package bytes, but Windows may show an unknown publisher.

## Security scope and references

The signed envelope authenticates exact UTF-8 payload bytes with RSA/SHA-256. It pins product, channel, architecture, sequence, expiry, version, allowed repository asset paths, package size/hash, schema and optional Windows signer certificate. The client remembers the highest accepted sequence/version and rejects backward/inconsistent metadata. This is a bounded single-key protocol, not a claim of independent security review, protection against a compromised publisher machine/key, or complete TUF compliance.

The host's protected app installation is the bootstrap trust boundary. TLS and signatures both remain required. Redirects are restricted to the expected GitHub asset hosts; an infrastructure change may require a new manual Harbor release. Downloads never automatically execute web-supplied filenames or arbitrary paths. Release launch information stays under the profile's Updates folder and contains no passwords or account database contents.

Primary references: GitHub's release-asset link format (https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases), HTTP range semantics (https://www.rfc-editor.org/rfc/rfc9110.html), Windows trust verification (https://learn.microsoft.com/en-us/windows/win32/api/wintrust/nf-wintrust-winverifytrust), SignTool (https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool), and update rollback/freeze threat guidance (https://theupdateframework.io/docs/security/).
